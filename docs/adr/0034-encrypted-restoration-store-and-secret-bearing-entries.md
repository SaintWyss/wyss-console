# ADR 0034: Restoration data may hold secrets, only encrypted at rest

Status: Accepted (owner decision DN-01, 2026-10-19)
Date: 2026-10-19

## Context

Claude Code has no switch for a single hook. To turn one off and be able to turn it back on,
Wyss Console takes the entry out of the provider's file and keeps it. A hook entry is
configuration, but it can hold a secret: a token typed into a command, a header of an `http`
handler.

[ADR 0003](0003-event-envelope-v1-and-data-handling.md) says secrets and credentials never enter durable
storage. [ADR 0028](0028-product-direction-and-agent-configuration.md) §7 (decision D5)
superseded that sentence for restoration data and asked that the options be compared first.
Doc 11 §5 compared four strategies and recommended refusing entries that may hold a secret
(D) with minimal private records (A) for the rest. The owner has decided otherwise.

## Decision (DN-01)

Wyss Console **may persist configuration entries that contain secrets**, provided they are
**encrypted at rest** with authenticated encryption and a key that is managed by the
operating system's credential store. This is strategy B of doc 11 §5.3.

1. **Authenticated encryption.** Every restoration record is sealed with ChaCha20-Poly1305
   under a 256-bit key. The nonce is random and never reused; the associated data binds the
   ciphertext to its record identifier, record kind and format version, so a record cannot be
   swapped for another or replayed as another kind. A record that fails authentication is
   never parsed and never partially shown.
2. **Key management.** The key is generated by the Console from the operating system's
   random source and stored in the **Secret Service** (KWallet or GNOME Keyring) under the
   service `wyss-console`. It is never written to the Console's state directory, a journal, a
   log, a diagnostic or a record, in any form. It lives in memory only while a record is being
   sealed or opened and is overwritten afterwards.
3. **No silent plaintext.** There is no setting, environment variable or fallback that stores
   a secret-bearing entry unencrypted.
4. **Fail closed.** If the key store is missing, locked and not unlocked, or answers
   something unexpected, an entry **classified as possibly holding a secret** is not parked.
   The plan says so in plain words, and the user is offered what remains: the coarse switch
   (`disableAllHooks`) or editing the file himself.
5. **Entries classified free of secrets** are also sealed when the key store is available.
   When it is not, such an entry may be kept as a private file (mode 0600, directory 0700)
   **only if the plan says so before the user confirms**. The classifier is conservative: doubt
   counts as "may hold a secret". Its measured pass rate on a labelled corpus is a test
   (TS-SEC-07).
6. **Provider-native state first.** Where a provider has its own switch (Codex hooks,
   skills, plugins, MCP switches, `disableAllHooks`, `skillOverrides`) nothing is stored
   anywhere: the provider's own mechanism is used.
7. **Never in the open.** Secrets and values never appear in the journal, in logs, in
   diagnostics, in an event, in an error, or in any projection that reaches the window. The
   window is shown that an entry "holds hidden values", never the values. The restore plan
   shows the entry redacted by the rules of 06 §4.2.
8. **Restore, undo, delete, integrity, recovery.** Restoring and undoing work from a sealed
   record and the journal; a record can be deleted by the user, and expires by the bounds of
   doc 14 §3; integrity is the authentication tag plus the hashes in the journal; an
   interrupted write is repaired at start by comparing the file's hash with those in the
   journal's intent.
9. **Export and import.** An exported record is sealed again under a key derived from a
   passphrase the user types in a native dialog (PBKDF2-HMAC-SHA256, random salt), so it can
   be restored on another computer. The passphrase is never stored. The file is written where
   the user chose in a native dialog.

## Threat model

| Adversary                                                              | Outcome                                                                                                                                 |
| ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Another user of the computer                                           | Reads nothing: directory 0700, files 0600, content encrypted                                                                            |
| A backup, snapshot or replication tool that copies the state directory | Gets ciphertext, not the key, which is in the credential store                                                                          |
| Someone with the disk offline                                          | Same; the key store is unlocked only by the user's session                                                                              |
| A process of the same user while the credential store is unlocked      | **Can ask the store for the key and read records.** It can already read the original provider file. No protection is claimed against it |
| A compromised page                                                     | Never receives a value or the key; cannot apply a plan that needs the native dialog                                                     |
| A modified record                                                      | Detected by the authentication tag; refused                                                                                             |
| A swapped or replayed record                                           | Detected by the associated data                                                                                                         |
| A bug report, log or diagnostic                                        | Holds closed words and counters; no value, no key, no content                                                                           |

## Consequences and limits

- **Key loss.** If the credential store is reset, the key is deleted, or the user's wallet is
  lost, **every sealed record is unrecoverable**. Parked entries cannot be put back by the
  Console; the journal still says what was removed and from where, without the content. The
  user is told before the first entry is parked that this is so, and the History view shows
  records as `key_lost` rather than hiding them. Plain exports made with a passphrase are the
  way to keep a copy that does not depend on the wallet.
- **Rotation.** The record header carries a key identifier. A new key can be generated; records
  sealed under an older one are re-sealed on use or by an explicit action. The prior key is
  kept in the store until no record refers to it.
- **Past copies.** Deleting a record deletes ciphertext; snapshots taken earlier keep it, and
  stay unreadable only while the key does.
- **A secret the classifier does not recognise** is treated as "free of secrets" and, if the
  key store is unavailable, may be kept as a private plaintext file with the disclosure above.
  This residual risk is the reason the fallback is disclosed and the classifier is measured.
- **Dependencies.** One AEAD crate, one key-derivation crate and the system's `secret-tool`
  (libsecret) at a fixed absolute path. No network.

## Future requirement: protected API credentials (not implemented)

A section of Wyss Console, **API Credentials**, will let the user add, replace, manage and
delete provider API keys. It is recorded here as an architectural requirement, **not built
now**, and it depends on this ADR:

- It reuses the key store and the sealing of this ADR, with its own record kind in the
  associated data, so a credential can never be read as a restoration record or the reverse.
- Values are typed in a native dialog and never in the page; the page lists names, providers,
  creation times and a fingerprint, never a value. Replacing and deleting need the native
  dialog. Nothing is shown again after it is saved.
- It needs its own ADR before it starts: how a credential reaches a provider (an environment
  variable of a process the Console starts, never written to the provider's own files),
  which providers, and the lifecycle of a managed runtime that uses one (ADR 0015 and the
  authority's isolation).
- Dependencies: this ADR's vault, the native dialog facility of F2a, and the execution plane
  decisions of F3a.

## What this does not decide

Whether the Console may write secrets into a provider's own files (it may not), and any use of
the credentials of the owner's providers (separate, explicit authorisation).
