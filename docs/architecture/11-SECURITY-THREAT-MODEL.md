# 11 — Security threat model

Domain K of [04](04-TARGET-ARCHITECTURE.md). Assets, boundaries, threats, controls, the
keeping of disabled entries and the handling of secrets. The managed plane's guarantees are in
[10 §2](10-MANAGED-RUNTIME-AND-SECURITY.md) and are not re-argued here. All `[P]` unless marked.

## 2. Trust boundaries

Those of [04 §2](04-TARGET-ARCHITECTURE.md). In one line each:

| Between                                | Trust                                                                    |
| -------------------------------------- | ------------------------------------------------------------------------ |
| Page ↔ backend                         | The page is untrusted input: it may be compromised by content it renders |
| Backend ↔ filesystem                   | Paths are untrusted until checked; contents are untrusted data           |
| Backend ↔ configuration adapters       | Adapters are our code; what they parse is untrusted                      |
| Backend ↔ native agents                | No boundary: same user. The agent can do whatever the user can           |
| Backend ↔ authority                    | The backend is a client with no authority over managed work              |
| Authority ↔ managed runtime            | The runtime is contained by a profile it must prove                      |
| Console ↔ remote clients (future)      | Authenticated devices with scoped grants; the network is hostile         |
| Anything ↔ external providers          | Model output is untrusted text everywhere                                |
| Anything ↔ system administrator policy | Trusted, read only, never bypassed                                       |

## 4. Authorisation of mutations

Risk is a property of the **plan**, computed in the backend from what the plan does.

| Class              | What falls in it                                                                                                                                                                                           | Confirmation                 |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| `normal`           | Switching a skill; switching off an MCP server or a plugin; switching off a non-blocking hook; a model preference                                                                                          | One confirmation in the page |
| `weakens_security` | Disabling a hook that can block an action; `disableAllHooks`; loosening a permission rule; anything the user marked as a control; starting a session with a profile that leaves out any of these (09 §3.1) | Native dialog                |
| `executes_code`    | Restoring or enabling a hook; switching on an MCP server or a plugin; later, creating or editing any of them                                                                                               | Native dialog                |
| `forbidden`        | Any write to a system source, a provider-owned file, a generated file or a trust record                                                                                                                    | Never offered                |

The native dialog states the provider, the scope, the file, the entry, the effect on running
sessions and on managed execution. What it shows is computed by the backend from the plan, and
its acceptance is valid for that plan identifier and that content hash only. It has no "do not
ask again" (ADR 0026 `:47` already rules that out for preferences `[R]`). The page learns only
the outcome. If the dialog cannot be shown, nothing is written (`dialog_unavailable`).

What this is and is not. The dialog is a second, separate place where the user consents. It
protects against a slip and against a defect confined to the configuration view. **It is not a
boundary against a compromised page**: code running in the page can write into a terminal
(`terminal_write`, ADR 0005) and edit the same file from the user's shell, with no dialog. ADR
0028 §5 says the check "protects the user's configuration from a compromised page"; that
sentence overstates it; the correction is proposed as ADR 0030 and is decision DN-22. The page's content policy
(CTL-27) is defence in depth and not a boundary either. A real boundary between the
configuration view and the terminal would need them to be separate web views with separate
capability lists; that is an option of DN-22, not designed here. The dialog is also not an
access control against the user or his other programs.

## 5. Restoration data and secrets

### 5.1 The problem, and where it stands

Claude Code has no per-hook switch `[D]`. To disable one hook and be able to put it back, its
entry has to live somewhere. A hook entry is configuration, but it can hold a secret: a token
written into a command line, a header of an `http` handler.

ADR 0003 says "Secrets and credentials never enter durable storage" (`0003:69-70`) `[R]`.
ADR 0028 recorded a supersession of that sentence for restoration data `[R]`. The owner then
stated a policy (2026-10-12) and, a day later, a decision (2026-10-13):

| Fixed by the owner                                                                                                         | Consequence for this design                                                                                                 |
| -------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| ADR 0028 is no permission to persist secrets; sensitive values go into no history, diagnostic or index                     | The journal and every index hold identifiers, hashes and times only                                                         |
| Restoration data is strictly minimised; provider-native mechanisms are preferred                                           | A native switch is used wherever one exists; nothing is stored for it                                                       |
| In-place keeping is preferred, **only if provider compatibility is verified**                                              | Keeping a disabled entry inside the provider's own file is the second rung, unavailable until tested                        |
| A heuristic detector is never taken to prove that hook content holds no secret                                             | Every entry is treated as possibly holding one. No copy is ever justified, or left in clear, because a classifier passed it |
| The last-seen index is not a duplicate of the owner's hooks                                                                | It holds no content; an entry removed from outside is not restorable from this computer                                     |
| **A protected private backup may be kept for exact restoration, with security controls and informed consent** (2026-10-13) | The third rung: the protected restoration vault ([27](27-PROTECTED-RESTORATION-VAULT.md))                                   |
| Where none of that can yet be done safely, the operation is unavailable, as a temporary state                              | The fourth rung; the window says what would enable it                                                                       |

What is still a proposal is the whole mechanism:
[ADR 0029](../adr/0029-secrets-restoration-data-and-configuration-persistence.md), **Proposed**,
in its second draft. Until it or another ADR is accepted, ADR 0003 is read at full strength and
no mutation is built (decision DN-01).

### 5.2 Who can read what

| Who                           | A disabled entry kept in the provider's own file (rungs 1, 2)                                              | An entry sealed in the vault (rung 3)                                                                                                                 |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Another user of the machine   | As the file's mode allows; the Console reports a mode that lets others read, and does not change it        | Nothing: modes, and ciphertext behind them                                                                                                            |
| A process of the same user    | Reads it, as it read the enabled entry                                                                     | **Reads it**, while the key can be obtained from the keyring or from the Console's memory                                                             |
| A backup or snapshot          | Captures what it already captured; a disabled entry stays in later snapshots where a deleted one would not | Captures ciphertext, in a place that did not hold the entry before. Readable with the key                                                             |
| A replication tool            | Carries it with the file, as it carried the enabled entry                                                  | Must not reach it: the vault is refused under the marker of a recognised tool. An unrecognised one is not detected; what it would carry is ciphertext |
| Someone with the disk offline | Reads it, as before                                                                                        | Ciphertext; readable to the strength of the keyring's password or of the passphrase                                                                   |
| A support bundle              | Not included: bundles hold no file content                                                                 | Not included: the builder cannot read the vault                                                                                                       |
| The page                      | The redacted projection of the inventory                                                                   | Metadata, and the same redacted projection. Unredacted content is shown only by a native dialog                                                       |

Keeping the entry in place adds **a longer life** and nothing else. Sealing it in the vault
adds **a second place**, protected at rest and not against a live process of the user. In both
cases a hook disabled because it held a leaked token still holds it: the interface says so when
the user disables one, and offers deletion as a different action.

### 5.3 Strategies

Compared in full in ADR 0029 ("Alternatives considered"). In short:

| Strategy                                | Status                                                                                        |
| --------------------------------------- | --------------------------------------------------------------------------------------------- |
| N. The provider's own switch            | First rung: used wherever it exists                                                           |
| I. In place, in the provider's own file | Second rung: proposed; unavailable per provider version and cell until verified (ADR 0029 §5) |
| B. An encrypted copy: the vault         | Third rung: approved as a requirement on 2026-10-13; its contract proposed (27); not built    |
| D. Refuse                               | Fourth rung, as a temporary state with its reason                                             |
| A. A private copy in clear              | Not adopted: it stores in clear what cannot be shown free of secrets                          |
| E. A sidecar file beside the provider's | Not adopted: the directory is replicated, and the provider may read the file as configuration |

### 5.4 The detector's remaining role

A detector of secret patterns (handler types with headers or credentials, an environment
assignment, a long random-looking token, a URL with user information) is still needed, for one
purpose: deciding what is **masked on screen** and warning the user. Its misses are displayed to
the user, in his own window, and are not persisted or logged by the Console. Its measured miss
rate on a labelled corpus is reported (§6). No decision to store, and no decision to store in
clear, depends on it: the vault seals every entry the same way, whatever the detector thinks.

### 5.5 What may be stored, and what never

The eight categories of ADR 0029 §2, as they apply to each store.

| Store                      | May hold                                                                                                                                                                                                               | Never holds                                                                                                                                                                                                                                                                                                      |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Journal                    | Provider, scope, source identifier, kind, event name if known to the adapter, ordinal position, operation, **keyed** digests of the file before and after, the identifier of a vault record, time, outcome, error word | Content of any entry; a command, matcher, URL, header, value; a path outside the provider's known files; an unkeyed digest of a file or of an entry                                                                                                                                                              |
| Last-seen index            | Per source: a keyed digest of the file, the time, one keyed digest per entry present in the file                                                                                                                       | Any content; anything from which an entry could be rebuilt; the digest of an entry that is no longer in the file                                                                                                                                                                                                 |
| **Vault records**          | Sealed: the removed span of a disabled entry and what places it back; a recovery copy of an entry the user selected (27 §3.3, §3.6). In clear: an authenticated header of identifiers                                  | Anything not needed for a restoration; anything the user neither disabled nor selected; a whole file, except a conflicting version; any credential file                                                                                                                                                          |
| Vault index, consent       | Identifiers, class, state, times, keyed digest, the policy consented to                                                                                                                                                | Content; an unkeyed digest of content                                                                                                                                                                                                                                                                            |
| Session registry           | Agent, project path, profile id and version, times, exit code                                                                                                                                                          | Command lines typed by the user; terminal content; environment values                                                                                                                                                                                                                                            |
| Profiles                   | References and names                                                                                                                                                                                                   | Secrets; copied instruction text; copied entries                                                                                                                                                                                                                                                                 |
| Generated session files    | Outside the Console's state directory and outside the vault. Whether they may exist at all when they would have to copy hook entries is DN-20                                                                          | —                                                                                                                                                                                                                                                                                                                |
| Transient files of a write | A copy in clear of the one file being replaced, in the Console's private transaction directory, for the duration of the write (07 §5.4; 28 §7). The second named exception of ADR 0029 §1                              | Never in a provider's directory; never after a final outcome, except in a recovery incident (07 §5.4)                                                                                                                                                                                                            |
| A conflicting version      | Sealed in the vault (28 §6)                                                                                                                                                                                            | Never a file beside the provider's file; never in a replicated directory; never kept in clear as a way of preserving it. After an unexpected sealing failure it is the evidence of a recovery incident, in clear in the private transaction directory, disclosed as a risk and never destroyed by time (07 §5.4) |
| Logs, diagnostics          | Closed error words, counters, versions                                                                                                                                                                                 | Paths outside known provider locations; any file content; any value; any digest derived from entry content                                                                                                                                                                                                       |

A digest of an entry is keyed with a random value made per installation (ADR 0029 §2): it lets
this installation recognise an entry and is left out of anything that leaves the machine.

Never logged anywhere: a credential, an environment value, a header, a prompt, terminal bytes,
a diff of a configuration file, a provider's raw output, a vault key, a decrypted record.

Provider credential and sign-in files are outside all of this: no adapter opens them (CTL-06),
so nothing of them can reach any store, the vault included.

## 6. Validation of the model

| Claim                                                                                   | How it is checked                                                                                                                       |
| --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| No secret reaches the page                                                              | TS-SEC-01: a corpus of fixtures seeded with marker secrets in every secret class; the serialised projection is searched for the markers |
| No secret reaches a store                                                               | TS-SEC-02: the same corpus through every operation; every store is searched                                                             |
| The page cannot cause an arbitrary write                                                | TS-SEC-04: every command's request type is enumerated and has no free path, content or command field                                    |
| A risky plan cannot be applied without the dialog                                       | TS-SEC-05: `apply` on such a plan with the dialog stubbed to refuse writes nothing                                                      |
| The engine and the authority are apart                                                  | TS-SEC-03                                                                                                                               |
| Filesystem attacks                                                                      | TS-FS-01 to 06 (20 §3.3)                                                                                                                |
| The detector of §5.4                                                                    | A labelled corpus; the measured rate of secrets it fails to mask is reported, not assumed zero. It gates no persistence                 |
| No entry content is on disk in clear after any operation                                | TS-VLT-01, with a control: a record written in clear on purpose must fail it                                                            |
| No fallback of the vault's protection                                                   | TS-VLT-15, 16, with a control: a build with a fallback enabled on purpose must fail                                                     |
| An entry exists in the file or in the vault at every instant                            | TS-VLT-17: fault injection between every pair of steps of 27 §8.2                                                                       |
| The vault's interface gives the page no content and no key                              | TS-VLT-05, 06                                                                                                                           |
| Code in the page cannot make, open or remove a vault record                             | TS-VLT-25: every such command called directly, with the native dialog refusing, changes nothing                                         |
| No store holds an unkeyed digest                                                        | TS-VLT-27                                                                                                                               |
| No copy in clear of a file is left by a write outside the private transaction directory | TS-WR-12, with stops at every step                                                                                                      |

## 7. Residual risks accepted, to be confirmed by the owner

1. A same-user process can do everything the Console can, without it. It can also reach the
   vault's key while the keyring is unlocked.
2. A user can confirm a dialog without reading it.
3. A secret the user wrote into a field shown as configuration is displayed to him.
4. A provider that writes its file at the same moment as the Console. No protocol prevents it;
   the candidate protocol names most orderings, and the ones it cannot see are classified in
   [28 §5](28-CONCURRENCY-AND-FILESYSTEM-INTEGRITY.md). Not to be accepted before DN-21 is
   decided.
5. A disabled entry that held a secret still holds it: in the provider's file, or in the vault
   and in every backup of the vault, until the user deletes it; and deleting it from the vault
   does not reach those backups.
6. A provider can change the meaning of a setting without changing its format.
7. A compromised page can type into a terminal, so the native confirmation is a safeguard
   against mistakes, not a boundary against the page (ADR 0030, proposed).
8. On the third rung the Console is the only holder of an entry. A lost vault or a lost key
   loses it; if it was a blocking hook, a protection is gone until the user writes it again.
9. The vault is worth what the key's custody is worth. A keyring that opens without a password
   protects a copied disk no better than a plain file.
10. A hook held in one computer's vault cannot be restored on the other.

## 9. Critical trust-boundary and remote threats added after REJECT (2026-10-14)

and [Claude report on separate branch](https://github.com/SaintWyss/wyss-console/blob/santiagosw/tender-albattani-udd3ir/docs/architecture/reviews/2026-10-14-external-audit-post-reject-corrections.md)
are REJECT reviews; the second remains on a separate unmerged branch
and its link may not resolve on the PR branch. Neither is an
executed exploit.

| Threat ID | Threat actor / path                                                                                                            | Asset and real boundary                          | Status / required gate                                                                                                                                                                                                                                    |
| --------- | ------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T-42      | Malicious manually launched native agent (not only OL3) reaches the same-UID control socket and submits owner-looking approval | A4; ADR 0011 same UID provides **no** separation | **BLOCKED_TRUST_BOUNDARY**. Inventory _all_ native/manual/remote processes, socket request paths, writable authority binaries/DB/units/config, impersonation flows. Per-attempt host review of **actual prompt and changed workspace/control source**; downstream effects must be independently constrained                                                         |

| T-48      | Managed-turn id/capability and native full-account identity collapse under same user in selected multi-runtime target          | A4; authority gating vs user principal           | ADR 0012/0015 remain active; concurrency and human-authentic approvals require separate threat model and ADR, not merely TS-ORC-11                                                                                                                        |
| T-49      | Android attestation absent, spoofed or not verified by host; controller grants LP4 based only on possession                    | A9/A5; device→gateway                            | Default deny LP4 unless appropriate per-use key validation and physical evidence; same-UID server compromise remains outside device attestation boundary                                                                                                  |

**Important correction to optimistic older controls:** the table above is
a proposed threat register, not a set of mitigations currently
implemented. `CTL-04` native dialog, `SO_PEERCRED`,
same-user file mode 0600 and a separate UI component
do **not** prove human presence against a compromised
same-UID native process (especially in a mutable desktop session).
`terminal.write` inherently grants owner account effects
including modifying the gateway/state if same UID.

A future proof for T-42 must test both legitimately permitted
native and managed workflows and denied same-UID impersonation.
A test that merely disables every native process is not a
final-product acceptance of DN-15.
See [42](42-POST-REJECT-CORRECTIVE-PLAN.md) for current
conservative gates. No ADR accepted, no tests run.

## 10. Elevated host-user authority through Docker on CachyOS (2026-10-14)

The [native CachyOS report](reviews/2026-10-14-cachyos-native-feasibility.md)
observed the logged-in Linux user has group-access to the **rootful**
`/run/docker.sock`, with `dockerd` running as real UID 0.
Docker's own documentation warns group `docker` grants
root-level privileges:
https://docs.docker.com/engine/install/linux-postinstall/

| Threat ID | Capability/asset                                                                                                         | Correct boundary and evidence status                                                                                                                                                                                                                                  |
| --------- | ------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T-50      | Unrestricted native agent or LP4 gains root-equivalent operations through user's pre-existing Docker daemon permissions  | **BLOCKED_ADMIN_DELEGATION**: same-host different UID is insufficient to protect authority binary, service, DB, verifier/signing material from an attacker able to use rootful Docker. This is a _threat-model consequence_, not an exploited host in the test        |
| T-51      | A restricted OL3 worker inherits Docker socket, another connected FD, host D-Bus/X11 bridge or another privileged broker | Bubblewrap omitted the Docker/socket paths in synthetic tests, but full inherited capabilities, alternate IPC paths and actual provider extensions remain unproved. Missing mount only protects that sandboxed process, not any unrestricted same-UID process outside |
| T-52      | Remote LP4 account compromise gains elevated host privileges beyond ordinary user files                                  | Consent and lost-device recovery must disclose possible **root-level Docker delegation**, not claim gateway revocation restores integrity                                                                                                                             |

Further design and tests are in
[47](47-CACHYOS-DOCKER-PRIVILEGE-AND-SANDBOX-DECISION.md).
Do **not** remove Docker group membership, contact its live socket,
restart services or probe privileged containers as part of
the documentation review. A migration to rootless Docker or
separately authenticated privileged access is a _future owner
choice_ requiring compatibility and rollback review.
