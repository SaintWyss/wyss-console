# 28 — Concurrency and filesystem integrity contract

What Wyss Console can and cannot promise when it writes a file that a provider, a replication
tool or another program may write at the same moment. It is the contract behind decision DN-21.
The protocol it examines is SM-WRITE, whose one normative description is
[07 §5.4](07-CONFIGURATION-ENGINE.md): this document adds no step to it and describes no other
variant. All `[P]`. Nothing here was run, and no timing in this document is a measurement:
where a duration matters, it is named as unmeasured.

**SM-WRITE is a design candidate, not a verified implementation, and DN-21 is technically
unverified.** There is no claim of zero data loss in this document, and no claim that every
concurrent write is detected. A writer that does not cooperate cannot be made to obey a lock it
never takes.

The owner's directions that this contract follows (2026-10-13): one canonical candidate for
direct edits, the one that keeps the previous file under a name through a bounded settling
time; a provisional strict mode; never an ordinary rename; transient copies in clear only where
indispensable and under an explicit, narrow exception; a conflicting version preserved in the
encrypted vault; and, where a required control cannot be established, the direct write refused.

## 1. Terms

| Term                  | Meaning                                                                                                                               |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| T                     | The provider's file being changed                                                                                                     |
| F0, h0                | Its content and digest when the plan was computed                                                                                     |
| F1, hp                | The content the Console intends, and its digest                                                                                       |
| X                     | Any other writer: the provider, a second provider process, a replication tool, an editor                                              |
| Fx                    | What X wrote                                                                                                                          |
| old file              | The file object that held F0. After the exchange it is under the operation's name in the private transaction directory, not under T's |
| transaction directory | The Console's private directory, on T's filesystem, where a write keeps its files (07 §5.4)                                           |
| settling              | The time after the exchange during which the old file keeps its name and is watched. It has a fixed ceiling. **Not measured**         |

The Console's intended change is one of three kinds, and the kind decides how bad a loss is:

| Kind          | Example                                                | If the Console's change is lost              | If X's change is lost        |
| ------------- | ------------------------------------------------------ | -------------------------------------------- | ---------------------------- |
| Weakening     | Disabling a blocking hook; `disableAllHooks`           | The protection stays: safe                   | Depends on what X wrote (§5) |
| Strengthening | Restoring a blocking hook; switching a control back on | **The protection is believed on and is not** | The same                     |
| Neutral       | A skill, a model preference                            | An inconvenience                             | The same                     |

reported to the user in the words of a higher one. None of the classes means "tested": nothing
is.

## 3. Why the old file keeps its name

The protocol keeps the displaced old file under a name, in the transaction directory, through
the settling time. That is the one design; this section says why, because it is what makes a
transient copy in clear indispensable.

| If the old file had no name during settling (rejected)                                                                            | With the old file named (the protocol of 07 §5.4)                                                 |
| --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| A rollback could only copy what is read through a descriptor. X may still be writing: the copy can be a version nobody ever wrote | The two names are exchanged back: **the same file** is T again, and X's writes keep landing in it |
| A file without a name cannot be given one again, so the old file itself could never be put back                                   | It never loses its name before it is verified and released                                        |
| A stop of the process during settling would lose the old file and anything X wrote into it, with nothing left to examine          | The file is found under its name at start and examined (14 §4)                                    |

The price is a whole copy of the file, in clear, under a name, for the settling time. It is the
file's own previous content; the protocol puts it in the Console's private directory and never
beside the provider's file. The exception that allows it is ADR 0029 §1 (proposed), and its
conditions are §7.

## 5. Losing a security control

The only losses that matter beyond inconvenience, each with its class.

| ID  | What happens                                                                                   | Example                                                                                  | Direction                                                   | Can it be silent?                                                                                          | Class                                               |
| --- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| L1  | A provider's write into the old file, after it was released, is lost (case 4)                  | The provider persisted a rule the user had just chosen in its prompt                     | Safe if the rule allowed something; **unsafe if it denied** | **Yes: nothing shows it**                                                                                  | G-N; G-P and G-E decide whether it can occur at all |
| L2  | A strengthening change of the Console is replaced by the provider's older version (cases 5, 6) | The user restores a blocking hook; a session that held the old settings writes them back | **Unsafe**: the control is believed on                      | Not while the Console is open: the watcher reports it. **Silent while it is closed**, until the next start | G-N                                                 |
| L3  | A weakening change of the Console is replaced the same way                                     | A disabled hook comes back                                                               | Safe                                                        | The same                                                                                                   | G-N                                                 |
| L4  | A stop of the process during settling together with a write into the old file (case 10)        | —                                                                                        | As L1                                                       | No: the old file has a name and is examined at start. A write after that examination is L1                 | G-D for the examination                             |
| L5  | The other computer's version replaces T                                                        | A hook restored here is absent again after replication                                   | Either                                                      | As L2                                                                                                      | G-N                                                 |

L1 cannot occur with a provider that always writes by replacing the name: there is then no
write into an old file. Whether each provider does so is OQ-31, and it is the single
observation that most changes this table.

**L1, L2 and L5 are unresolved technical blockers**, by the owner's word (2026-10-13). They are
not open questions that a better protocol would close: L2 and L5 follow from writers the
Console does not control, and L1 can be ruled out only by observing that a provider never
writes a file in place. Nothing in this set claims that no change is lost or that every
concurrent write is detected.

Rules proposed for a file that holds a blocking hook, a permission rule or anything the user
marked as a control:

| Rule                                                                                                                                                                                                                             | Against |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------- |
| A strengthening change is reported "written" and then checked again: at the end of settling, at the next observation of the file, and when the window next takes focus. Only then is it shown as in place                        | L2, L5  |
| At every start the last applied operation of each source is compared with the file; a change that is no longer in place is reported before anything else about that source                                                       | L2, L5  |
| A weakening change is never applied again automatically; a strengthening change is offered again, never applied by itself                                                                                                        | L2, L3  |
| **Strict mode** (§5.1): a risky write is refused while a known session of that provider is active. Adopted provisionally by the owner's direction of 2026-10-13. Relaxing it is his decision, taken with the observations of §10 | L1, L2  |

### 5.1 Strict mode, as provisionally adopted

| Term            | Meaning here                                                                                                                                                                        |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A risky write   | Any mutation of a file of that provider that can hold a hook, a permission rule or an entry the user marked as a control. In practice its settings files, until evidence narrows it |
| A known session | A native session the Console started and still sees running (05 §5); and a process of the same user whose executable is that provider's, found by reading the process list          |
| Active          | Seen when the write is prepared, and again immediately before the exchange (07 §5.4, `preparing` and `checked`)                                                                     |

| Strict mode does see                                  | Strict mode does **not** see                                                                |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Sessions started from the Console                     | A provider embedded in another program: an editor extension, a script that uses its library |
| The provider's own processes under the user's account | A background or scheduled run that starts a moment after the check                          |
|                                                       | Sessions on the other computer, and what replication delivers from it                       |
|                                                       | Any other writer: an editor, a script, another tool that manages the same file              |

**Strict mode is not a proof.** It is not a proof against a race, against a background process,
against the replication tool or against a writer that does not cooperate. It removes the most
likely overlap, a provider session the user has open, and nothing more. The protocol of
07 §5.4 still runs under it, because the writers it does not see are still there.

What it costs is stated to the user in the refusal: "Close your Claude Code sessions to change
this." It is the use the product was asked for, changing a hook while sessions run, that waits.
Relaxing it needs the observations of §10 and the owner's decision.

## 6. Preserving a version that cannot be put back

A write can end holding a version of T that is in no provider file. After the corrections that
is one case only: the target was replaced by a third version **and** the old file was written
too. Every other conflict is settled by exchanging the names back, with no sealing.

The owner's decision on DN-28 (2026-10-13):

| #   | The contract                                                                                                                                                                                                            | In the design                                                                                                |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 1   | Staging artefacts in clear exist only for the bounded time strictly needed to finish a transaction or roll it back safely                                                                                               | §7; 07 §5.4                                                                                                  |
| 2   | Persistent recovery of a conflict uses the encrypted vault                                                                                                                                                              | A `conflict_version` record (27 §3.1)                                                                        |
| 3   | If the protocol cannot securely preserve a possible conflict, that direct-write mechanism stays unavailable until the failure path is adequately designed and validated                                                 | **A gate, closed today.** Sealing is prepared before the write or the write is refused; the validation is 30 |
| 4   | If an unexpected failure after the mutation makes protected preservation impossible: a documented recovery incident. Conflicting writes blocked, recovery evidence preserved, both risks disclosed, controlled recovery | 07 §5.4, "Recovery incident"                                                                                 |
| 5   | Never report success, never silently destroy the only recoverable copy, never treat private storage in clear as equivalent to encryption                                                                                | The same                                                                                                     |
| 6   | No claim that zero exposure in clear and zero loss are both guaranteed where the environment does not support it                                                                                                        | This document makes none                                                                                     |

There is **no timeout** in this design. An earlier proposal destroyed a held version after a
fixed number of days; the owner rejected it, and rejected replacing it with another number.

| Step                             | Rule                                                                                                                                                                                                                                                                                                                                                        |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Before any direct write          | The vault must be ready, consent for a conflicting version on record, and a sealed placeholder of the file's size written and verified (07 §5.4, `preparing`). If not, the write is refused. What can be prepared before the mutation is prepared: the key, the storage, the space. The conflicting version itself cannot be, because it does not exist yet |
| When a version must be preserved | It is sealed as a `conflict_version` record, read back and verified; only then is its name in the transaction directory removed. Outcome `conflict_preserved`                                                                                                                                                                                               |
| If sealing fails at that moment  | A recovery incident (07 §5.4). Nothing is destroyed and nothing expires                                                                                                                                                                                                                                                                                     |
| Never                            | A file beside the provider's file. A file in a directory that is replicated. A version destroyed by the engine. Success reported                                                                                                                                                                                                                            |
| Resolution, by the user          | See both versions in a native dialog; make one of them the file, which is a new plan through SM-WRITE; save the kept one where he chooses; or delete it, knowing it is the only copy                                                                                                                                                                        |

What is **not** established, and keeps the gate closed: that preparing the sealing makes it
succeed afterwards. On a copy-on-write filesystem a placeholder does not reserve the blocks a
later record will need, and an I/O error can come at any moment. Whether the failure path is
adequate is a question for validation, not for this text (30, TV-09 and TV-16).

## 7. The transient copy: the contract of the exception

Replacing a file without destroying what it replaces needs the old file to stay reachable under
a name (§3). That is the only thing a copy in clear is allowed for. The exception is stated in
ADR 0029 §1, proposed; this is its contract, condition by condition, as the owner set them on
2026-10-13. **It is a design, not a verified mechanism.**

| Condition                                       | How the design meets it                                                                                                                                                                                                                                                                                     | Status                                       |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| Minimal lifetime                                | The new content has no name while it is written; it has one from one call to the next. The old file has one from the exchange to the end of settling, which has a fixed ceiling, and never beyond it: at the ceiling it is released or sealed                                                               | G-D; the ceiling's value is G-E (OQ-31)      |
| Necessary content only                          | The one file being replaced. Nothing else is copied                                                                                                                                                                                                                                                         | G-D                                          |
| Restrictive permissions                         | Both files are in a directory of mode 0700 owned by the user, every ancestor checked. The staged file carries the target's mode because it becomes the target; the old file keeps its own; neither is reachable by another user through that directory                                                      | G-D; G-F for the modes                       |
| Safe handling of a stop or an interrupted write | Every stop has a row in 14 §4. A file in the transaction directory is identified by an open intent and by keyed digests, removed only when verified, sealed when it is a version nobody else has, and otherwise kept and reported                                                                           | G-D; TS-CFG-12 would test it                 |
| Filesystem and metadata guarantees              | Required and probed, per filesystem and per start: an atomic exchange of two names in two directories; unnamed temporary files that can be named; one filesystem for both directories. Mode, owner and attributes are carried or the write is refused                                                       | G-F; **unverified on the owner's computers** |
| A defined recovery procedure                    | 14 §4 and §4.1                                                                                                                                                                                                                                                                                              | G-D                                          |
| Protection against unintended synchronisation   | No file of a write is ever in a provider's directory. Where the transaction directory may be is judged by the criterion of 27 §9.1, which is open (DN-31): a marker above it is not proof of replication, and an ignore rule is not a guarantee. The Console never edits a replication tool's configuration | G-D for the placement; G-E for the detection |

What the contract does **not** cover, stated as limits and not as guarantees:

| Limit                                                                                                                                                                                                                                                                  | Class |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----- |
| The Console's state directory may be copied by a replication tool it does not recognise, by a backup or by a filesystem snapshot. On the owner's computers the home subvolume is snapshotted, so a file in clear there can be captured during a write (27 §9.1; 30 §6) | G-E   |
| A snapshot taken while a transient file exists holds it, in clear, for as long as the snapshot lives                                                                                                                                                                   | G-N   |
| Removing a name does not erase the bytes: on a copy-on-write filesystem and on flash storage they stay until reused                                                                                                                                                    | G-N   |
| If the Console stops and is never started again, the file it left stays in its private directory                                                                                                                                                                       | G-N   |
| A process of the same user can read the transaction directory                                                                                                                                                                                                          | G-N   |

Deployment assumption, to be said to the user: the Console's state directory is on the same
filesystem as the configuration it edits, and is excluded from replication, from snapshots and
from sharing. On the owner's two computers the first part is supported by inspection and the
snapshot part does not hold (30 §6). How the Console checks any of it is open (27 §9.1; DN-31),
and **no direct write is available until it is decided**. What the inspection found that blocks
a direct write, beyond the losses of §5, is listed in 30 §6.4.

A plain rename over T is not a fallback. It replaces whatever is under the name without looking
at it: a write by X between the check and the rename is destroyed, nothing is displaced that
could be examined, and reading T back shows the Console's own bytes and would be reported as
applied. That is the silent loss this contract exists to exclude, and what ADR 0028 §8 wrongly
says is detected.

## 9. The position on DN-21

The owner's directions of 2026-10-13, and the author's recommendation where he gave none.
**Nothing here is verified, and DN-21 is not closed.**

1. Where a provider has its own writer for the setting, and it is verified, use it and nothing
   else.
2. Otherwise SM-WRITE as 07 §5.4 states it: one protocol, the old file named through a bounded
   settling time, on filesystems that offer the primitives, with a private transaction
   directory on the same filesystem.
3. Never a plain rename, on any filesystem. Where the protocol cannot run, the direct write is
   refused.
4. Strict mode, provisionally: no risky write while a known session of that provider is active.
5. A conflicting version sealed in the vault; the vault ready, and sealing prepared, before any
   direct write. Reading, the inventory and a provider's own verified writer do not wait for it.
6. The rules of §5 for files that hold controls.
7. The sentence of ADR 0028 §8 corrected by [ADR 0030](../adr/0030-corrections-to-adr-0028.md).

What remains with all of it in place: losses L1 to L3 and L5 of §5. L2 and L5 are detected at
the next observation and never prevented, and are silent while the Console is closed. L1 is
undetected, and whether it can occur depends on a provider behaviour nobody has observed.
Strict mode makes L1 and L2 unlikely on one computer and does nothing for L5.

## 11. Tests

TS-WR-01 to TS-WR-20 ([20 §3.6](20-VERIFICATION-AND-ACCEPTANCE.md)) are written against the one
protocol of 07 §5.4, with a scripted second writer. They cover cases 2a, 2b, 4 (during
settling), 5, 9 to 14, 16 and 17. Two controls are required: a writer that only checks, renames
and reads back must **fail** TS-WR-01 and TS-WR-03; a rollback that copies what it reads
instead of exchanging the names back must **fail** TS-WR-13.

No test can show that case 4 after release, case 5 while the Console is closed, or case 6 is
handled: they are the cases the Console does not observe. The tests show what is done when a
write is seen, and they are not evidence that every write is seen.
