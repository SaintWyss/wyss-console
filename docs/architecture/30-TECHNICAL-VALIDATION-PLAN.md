# 30 — Technical validation plan

What has to be observed or tested before the protected vault
([27](27-PROTECTED-RESTORATION-VAULT.md)) and the direct-write protocol
([07 §5.4](07-CONFIGURATION-ENGINE.md), [28](28-CONCURRENCY-AND-FILESYSTEM-INTEGRITY.md)) can be
relied on. A plan for a future phase. `[P]` throughout.

**This plan authorises nothing.** Nothing in it has been run, apart from the read-only
inspections recorded in §6 and §7 and the single probe of §8. Each group below needs its
own authorisation from the owner, and the last one needs provider binaries, which are
explicitly not authorised (22, DN-24). Passing an item validates that item; it accepts no
ADR and overturns no review.

The design stops being revised here. What this plan finds goes back as findings, to be decided
by the owner, not as silent edits.

## 1. What validation can and cannot settle

| Can be settled by validation                                                                            | Cannot                                                                                                                                     |
| ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Whether the filesystem primitives exist and behave on the owner's computers                             | **L2 and L5**: a provider, or the other computer, replacing a change while the Console is closed. They follow from writers nobody controls |
| Whether a stop at any step leaves a state that repair names                                             | That every concurrent write is detected                                                                                                    |
| Whether the path that preserves a conflict works, and what happens when it does not (the gate of DN-28) | That no change is ever lost                                                                                                                |
| Whether a given provider version ever writes a file in place, which decides whether **L1** can occur    | L1 for a version that was not observed, or for a writer other than the provider                                                            |
| What the owner's keyrings are worth                                                                     | Anything against a process of the same user                                                                                                |

L1, L2 and L5 stay **unresolved technical blockers** whatever this plan returns (28 §5). The
most it can do for L1 is show that it does not arise with one provider version.

### 8.5 What this settles, and what it leaves

**The alternative "a subvolume of its own for the transaction directory" is withdrawn from
DN-31.** With a mount of its own it is refused by a test on both computers. Nested in the
home it was not tried: it is withdrawn as well, on the kernel's source, and for a reason that
needs no test, that it would have the Console depend on a change to the layout of the owner's
filesystem. If the owner wants the nested case reopened, the test is one throwaway subvolume,
created and removed, which he has not authorised.

Withdrawn with it: every place for a staged file outside the home subvolume. The filesystems
in memory, `/var/tmp`, `/srv` and the data disk are all across a mount.

What follows: a staged file that can be exchanged with a provider's file is in the home
subvolume, and so inside any snapshot of the home (§7.5). **That is not an acceptance of the
exposure.** The owner's instruction of 2026-10-13 is that the snapshot exposure is not taken
as the substitute by default. DN-31 stays open until he resolves the trade-off between storage
and security.
