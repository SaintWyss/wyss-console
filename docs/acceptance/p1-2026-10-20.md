# P1: backend measurements, an idle-cost optimization, and what is still not measured

2026-10-20, `saint-acer` (Intel i5-10300H, kernel 6.18.55-2-cachyos-lts, on mains power), the owner's
normal desktop with their other applications open and 11–12 GiB of swap in use. Follows
`p1-2026-10-19.md`. **P1 remains open. No budget is declared passed.** These are measurements of one
machine under real, uncontrolled conditions, with every condition recorded beside its figure.

## What was added

`benchmarks/` gained a backend harness (`src-tauri/src/terminal/bench_tests.rs`, ignored tests run
by hand in release), `aggregate.py`, `threads.py` (per-thread processor time and wake-ups) and
`idle_ab.py` (originally `idle-ab.sh`, replaced after the incident below). The backend tests run the real PTY and the real `TerminalService` in one process, with
**no window, no WebKit and no renderer**: every figure below is the backend's, labelled so. Corpora
(BC-01 plain ASCII 64 MiB, BC-02 dense colour 16 MiB, BC-03 wide characters 16 MiB, BC-04 very long
lines 8 MiB) are generated from a fixed seed. Nothing is removed from a sample list.

## The measurement that found something: idle wake-ups

`threads.py` on the **real, running host** (PID 1188641, one idle fish terminal, nobody attached):

| Thread          | CPU of one core | Wake-ups per second |
| --------------- | --------------: | ------------------: |
| accept loop     |          0.550% |               193.3 |
| terminal pump   |          0.050% |                24.8 |
| PTY worker      |          0.050% |                24.8 |
| **host, total** |      **0.650%** |           **242.9** |

That is 0.65 % of a core for a process that holds an idle shell, which is more than the idle
Ghostty root of the earlier comparison (0.25 %). Causes (read in the code, then reproduced): the accept
loop slept 5 ms and asked again; the pump asked the terminal again every 4–40 ms; and each ask also woke the
PTY worker. Changes: the accept loop `poll`s its listener (250 ms bound), the pump waits on a new
`TerminalService::wait_for_output` (one second bound) instead of sleeping, and the page's output pull
is a long poll (below). In-process, with a test that fails on the earlier code
(`a_host_with_an_idle_terminal_waits_instead_of_polling`):

| Thread      | Before | After |
| ----------- | -----: | ----: |
| accept loop |  195.0 |   3.8 |
| pump        |   24.8 |   0.8 |
| PTY worker  |   24.8 |   9.8 |

(The first column reproduces the live host's figures, 193/25/25.) The PTY worker still looks at its
child a few times a second to see it exit; that was left alone. Total host wake-ups at rest:
**243 → about 14 per second.** The real host was not replaced (below); its CPU after the change was
not measured as a process, only its wake-ups in the test.

The page asked the desktop for output every 320 ms at rest (three times a second per terminal, each
through the webview, the desktop and a host connection), and the desktop asked the host with `wait_ms: 0`.
The desktop now asks with a one-second wait and the page does not pace a pull that was already a wait
(an answer that comes back at once is still paced). Idle, window shown, Console view, one adopted terminal,
60-second windows, builds before/after alternating three times on an isolated display (the real host, unchanged,
behind both):

| Run       | WebKit web process: CPU / wake-ups per s | GUI process: CPU / wake-ups per s |
| --------- | ---------------------------------------: | --------------------------------: |
| A1 before |                           0.567 % / 62.9 |                   0.383 % / 134.7 |
| A2 before |                           0.717 % / 72.0 |                   0.383 % / 134.1 |
| A3 before |                           0.683 % / 83.1 |                   0.350 % / 134.7 |
| B1 after  |      0.583 % / 245.7 (**outlier, kept**) |                   0.267 % / 107.1 |
| B2 after  |                           0.317 % / 42.1 |                   0.250 % / 106.4 |
| B3 after  |                           0.300 % / 36.5 |                   0.233 % / 106.6 |

Medians: web 0.683 % → 0.317 %, GUI 0.383 % → 0.250 %; **web plus GUI about 1.07 % → 0.57 % of one core
(about −47 %)**, with B1 as a visible exception whose cause was not found (it did not repeat). Three runs per
build on a software-rendered nested display are an observation, not a confidence interval; they say the
direction and its order of magnitude, not a budget. What remains in the GUI process is mostly WebKit's own
vblank monitor (46 wake-ups/s), the link to the authority (20/s, a short read timeout in its watch) and
page timers; the link's polling was left alone.

## Real-system check of the first A/B attempt (and an error of mine) — see the incident record

`docs/incidents/2026-10-20-benchmark-ended-live-session.md` is the authoritative account and the fix.

The first attempt took "its" GUI's PID with `pgrep -x -n wyss-console` and ended it. The binaries under
test had other names, so that matched the **owner's own running GUI and host**, which were terminated; the
rounds measured them instead (the owner's GUI idle read 0.317 % web / 0.483 % app in that window). I
restored the installed application (a fresh terminal tab; the earlier shell's in-memory state is gone),
discarded that attempt, rewrote the script to use only the PID of its own launch checked against the binary's
exact path, and re-ran. The owner's current PIDs were checked unchanged after the second set of runs.

## Still not measured (NOT_RUN, not zero)

M01/M02/M25 start-up (needs cache drops or reboots, and a build timestamp hook, OQ-26); M03/M04 hidden/shown
under controlled visibility on the real GPU desktop; M05 with two idle minutes; M07 native agent cost; M08
page-level input latency to a drawn glyph (external method, OQ-27); M11/M17 responsiveness under load; M13,
M20 resize and divider drag; M15 paste; M16, M19, M21–M24, M26–M33 (watcher, inventory, restore, search,
supervision, vault, direct write, repair, eight-hour stability, interface interaction, scrolling); renderer and
WebKit memory per terminal and per 5,000/50,000 lines of scrollback; the comparison with Ghostty beyond the
earlier idle figures. The isolated display renders in software, so its figures are not the real desktop's
GPU path. Bootstrap intervals exist only for the backend runs above. The change to the host is **not
installed**: the running host is the older one, and replacing it ends the owner's terminals.
