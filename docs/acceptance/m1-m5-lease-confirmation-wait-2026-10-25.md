## Root cause

Granting or renewing a lease that lets a runtime act is allowed by the user in a **native modal GTK window** first (`desktop/f8/confirm.rs`, finding W1). While that window waits (up to 5 minutes), the command is pending in Rust and the page showed only "Granting the execution lease…". The window is modal, so the main window ignores input, Alt+F4 included, until the user answers. The approval panel already said "Waiting for your Allow in the confirmation window…"; lease grant and renewal did not.

Measured on the real stack (packaged authority `wyss-control` + real Codex 0.159.0 Ready, diagnostic GUI on the real Wayland session, the window answered from inside GTK, **no OS input**):

| Window answered after (from when it opened) | Page pending | Rust returns → page clears | `main` loop stalls |
| ------------------------------------------- | ------------ | -------------------------- | ------------------ |
| 2.5 s                                       | 2.83 s       | ≈0.2–0.4 s                 | 0                  |
| 6 s                                         | 6.47 s       | ≈0.2–0.4 s                 | 0                  |
| 9 s                                         | 9.29 s       | ≈0.2–0.4 s                 | 0                  |
| 12 s                                        | 12.12 s      | ≈0.2–0.4 s                 | 0                  |

- The pending time equals the time the window is open; after Allow the authority answers in ~20–40 ms (reconnect included, so a window left open past the authority's 5 s idle timeout is not a problem) and the Tauri IPC promise settles at once (`ipc.headers`/`ipc.body` ms equal the Rust time).
- The page stays responsive while the window is open (IPC round trip 10–27 ms) and the GTK main loop never stalls; the window is `FOCUSED`/active when the app raises it (`confirm.dialog.probe`).
- No refresh waits on a blocked call: the Control link lock, the `blocking` pool and the authority's 5/16 s call bounds were read and traced; no unbounded wait exists on the grant path except the user's own window.
- The earlier run's authority store (kept by the owner in `~/wqz-jGaB/state`, copied read-only) holds **exactly one** `execution_lease.granted` (event 5, revision 2, five scopes, 5 min) and later one `expired`; the first attempt left none. So the grant was durably committed once, nothing was duplicated, and expiry was enforced. The `authority.sqlite3-journal` that stayed beside an idle authority is by design: `control/application.rs:145` sets `locking_mode=EXCLUSIVE` (an external `sqlite3` gets "database is locked" until the authority stops; after a clean stop there is no journal and `integrity_check` is `ok`).

So the reported symptoms match a confirmation window that stayed open and unseen: attempt 1 (no lease, main window ignoring Alt+F4, killed by PID) and attempt 2 (grant recorded once the window was finally answered; the screenshots y05–y08 are the same size to the byte, and the lease state was read only after a GUI restart, y09–y10).

**Not proven:** why the harness did not see or answer the window. The harness captured with `spectacle -a` and never mentions the window; on the real session the window is created focused, so it should have been in front. I cannot reproduce "window open but not noticeable" without a physical keyboard and pointer.

## Fix (`aab42c3`, frontend only)

- A grant with an acting scope, and every renewal, now says "Waiting for your answer in the confirmation window. Nothing is allowed until you choose Allow. If you cannot see it, it may be behind another window." (`OperationStep` `confirming`).
- The page bounds its wait for any answer: 90 s, or 5 min 30 s for an action the user must allow (Rust waits 5 min). On expiry the outcome is `unavailable` ("the outcome is not known", retry), the authority is read again, nothing is sent again by itself, and **retry sends the same identity**. An answer that arrives late clears the failure and is only read. Same bound on approval decisions. This is defence in depth for "no indefinite pending state"; no real lost response was observed.
- Unchanged: validation, the allowlist, the confirmation window, leases, fences, revisions, expiry, the authority and its protocol. No Rust change; no new command or permission.

Regression tests (all fail on `01b4f40`, pass on `aab42c3`): 8 in `tests/f8-controller.test.ts` (confirming step for grants with and without acting scopes and for renewals; lost grant → failed `unavailable`, authority re-read, one call; retry with identical arguments; late success clears and asks nothing; late failure keeps the failure and a second click does nothing; short bound cancelled on success; decision bounds and retry) and 2 in `tests/f8-view.test.ts` (banner text with and without acting scopes).

Checks: `npm run format:check`, `lint`, `typecheck` clean; `npm test` **1067/1067** (was 1057); `cargo fmt --check` ok; `npm run rust:clippy` (`--all-targets --features b1-fixture -D warnings`) finished with no warning, which completes the clippy run left open for `01b4f40` (the Rust is identical in `aab42c3`); `cargo test --lib desktop::f8 f8::gui` 24 passed. The full `rust:test` was not re-run in this session (Rust unchanged since the 1436 + 535 run reported for `01b4f40`).

## Remaining issues

1. **Medium (UX/security design):** the confirmation window is modal and the main window is blocked for up to 5 minutes with no way to cancel from it. The banner now says so; making the window non-modal with a Cancel in the page, or raising it (`present()`, urgency hint), is a product decision I did not take without evidence.
2. **Low:** capacity-one is reported as "busy… try again" with Retry; it should say another session holds the runtime.
3. **Low:** `wyss-console --help` ignores the flag and opens the GUI.
4. **Info:** the console's own "Choose folder" in the Agents view and in Runtimes are different commands (`native_choose_project`, `choose_workspace`); not a defect.
