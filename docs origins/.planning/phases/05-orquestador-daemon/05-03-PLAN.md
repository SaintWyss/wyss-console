<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| owner → wyss confirm | El owner resuelve una propuesta pending por id; debe rechazarse si ya expiró/resolvió |
| pending.db (disco) → daemon | La cola SQLite es la fuente de verdad; debe sobrevivir restart sin pérdida ni corrupción |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-07 | Tampering | confirmación de propuesta destructiva tras expirar (stale execution) | mitigate | `resolve()` solo procede si status='pending'; el ttl_reaper marca 'expired' antes; TTL más corto para C (D-56). Guard testeado (test_confirm_rejects_expired_proposal). |
| T-05-08 | Repudiation | propuesta expira sin rastro | mitigate | ttl_reaper loguea CONFIRMATION_ANSWERED por cada expiración con pending_id+risk_level (auditoría fail-closed). |
| T-05-09 | Denial of Service | pending.db sobre NTFS cae a journal mode sin WAL silenciosamente | mitigate | WAL fail-fast: raise AuditIntegrityError si journal_mode != "wal"; DB en ext4 del proyecto, no en ~/Data NTFS (Pitfall 4). |
| T-05-10 | Tampering | pending_proposals editable directamente | accept | DB local 0600 (hereda permisos del proyecto single-owner); no append-only como audit (status muta por diseño). |

Block on HIGH: T-05-07 (stale confirm) es el riesgo de mayor severidad; el guard de resolve() debe estar verde.
</threat_model>
